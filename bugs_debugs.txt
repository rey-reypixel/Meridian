======================================================

BUG 1 — Wrong FastAPI import name
----------------------------------
File:     app/dependencies.py
Symptom:  App would crash immediately on import/startup.
Cause:    Imported `HTTPAuthCredentials` from `fastapi.security`, but that
          class doesn't exist. The real class is `HTTPAuthorizationCredentials`.
Fix:      Changed import and type hint:
              from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
              ...
              credentials: HTTPAuthorizationCredentials = Depends(security)


BUG 2 — Async/sync DB session mismatch
----------------------------------------
Files:    app/api/routes.py, app/api/auth.py, tests/conftest.py
Symptom:  Would raise `AttributeError: 'AsyncSession' object has no attribute
          'query'` on every database-touching endpoint (/api/messages,
          /api/dashboard/summary, /api/dashboard/models, /api/requests/{id},
          /auth/callback). Even where `.commit()` exists on AsyncSession, it's
          a coroutine — calling it without `await` means the commit silently
          never happens (data loss), no crash, no warning surfaced to caller.
Cause:    Routes were injecting `get_db_session` (an async generator yielding
          `AsyncSession` from db/database.py) but all the ORM code written
          against it used synchronous SQLAlchemy patterns: `db.query(...)`,
          `db.add(...)`, `db.commit()` without await.
          Meanwhile `app/dependencies.py`'s `get_current_user` was already
          correctly using a separate *synchronous* `get_db` (backed by
          `SessionLocal`) — so the two auth/db paths were inconsistent.
Fix:      Standardized on the synchronous `get_db` dependency everywhere
          (matches how the ORM code is actually written):
            - routes.py: swapped `Depends(get_db_session)` -> `Depends(get_db)`
              for all 4 endpoints, imported `get_db` from app.dependencies.
            - auth.py: same swap for the OAuth callback route.
            - tests/conftest.py: test fixture now overrides `get_db`
              (was overriding `get_db_session`, which no longer matched any
              route dependency, so the test db swap was silently doing
              nothing before this fix).
Note:     `get_db_session` (async) is still defined in db/database.py for
          future use, just not wired into any route right now.


BUG 3 — Missing email-validator dependency
---------------------------------------------
File:     app/db/schemas.py (uses `EmailStr` from pydantic)
Symptom:  ImportError at import time: "email-validator is not installed,
          run `pip install 'pydantic[email]'`" — took down the whole app
          since schemas.py is imported by routes.py at module load.
Cause:    `pydantic.EmailStr` requires the optional `email-validator`
          package, which wasn't listed in requirements.txt.
Fix:      Added `pydantic[email]` to backend/requirements.txt.


BUG 4 — Missing numpy dependency
------------------------------------
File:     app/services/context_truncation.py
Symptom:  ModuleNotFoundError: No module named 'numpy'.
Cause:    File does `import numpy as np` (used for embedding vectors, ahead
          of full Phase 2 FastEmbed integration) but numpy was never added
          to requirements.txt.
Fix:      Added `numpy` to backend/requirements.txt.


BUG 5 (minor / code smell) — Mutable default on SQLAlchemy JSON column
--------------------------------------------------------------------------
File:     app/db/models.py
Symptom:  Not yet triggered in practice (routes.py always passes
          `optimizations_applied` explicitly), but a real landmine: SQLAlchemy
          column defaults should be callables, not shared mutable objects.
          Using a literal `[]` means every row that relies on the column
          default shares the *same* list instance.
Cause:    `optimizations_applied = Column(JSON, default=[])`
Fix:      `optimizations_applied = Column(JSON, default=list)`

DESIGN NOTE — batching vs. a synchronous HTTP API
--------------------------------------------------------------------------
Anthropic's real Message Batches API has ~24h turnaround, which doesn't
fit a request/response HTTP endpoint. Implemented instead: requests with
batch=true get pushed onto a Redis list keyed by (model, task_type); once
the group hits batch_size or sits past batch_timeout, a Celery task
(meridian.process_batch, in app/celery_app.py) pops the group and calls
Claude sequentially for each item in the *worker* container, storing each
result back in Redis under its own request_id. The original HTTP handler
polls (via run_in_threadpool, so it doesn't block the event loop) for its
own request_id's result.

Gap: there's no Celery beat/periodic flush (explicit Phase 2 scope
decision), so a batch with no further arrivals just sits until something
checks it. Safety net: if a request's own wait_for_result poll times out
(15s), it force-flushes its batch inline rather than hanging forever or
erroring for no reason. Verified both paths actually happen (see live
tests below) — a 2-request batch with batch_size=2 flushed for real via
Celery .delay() and showed up in the worker's logs; a lone 1-request
batch (nothing to fill it) correctly fell through to the inline fallback
after its wait timed out.

PHASE 2.5 — found while wiring up 3 previously-dead request params
======================================================
Date: 2026-08-08 (same day, continued)
Context: Before testing against a real Anthropic API key, checked whether
MessagesCreateRequest's advertised parameters (cost_limit, optimize_for,
quality_threshold) actually did anything. They didn't — 3 of 8 request
fields were accepted and silently ignored. Fixing all 3 surfaced two more
real bugs along the way.

BUG 6 — cost_limit accepted but never enforced
--------------------------------------------------------------------------
File:     app/api/routes.py (create_message)
Symptom:  A caller could pass cost_limit=0.50 ("don't spend more than
          this") and it did nothing — request always went through
          regardless of estimated cost. Directly contradicts the README's
          advertised budgeting feature.
Cause:    request.cost_limit was never read anywhere in the function.
Fix:      After computing optimized_cost (the pre-call estimate) and
          before any LLM/batch call, added:
            if request.cost_limit is not None and optimized_cost > request.cost_limit:
                raise HTTPException(402, detail=f"Estimated cost ... exceeds cost_limit ...")
          Placed before the Claude API call specifically so a request that
          would exceed budget never spends anything.
Test:     tests/test_routes.py::test_create_message_cost_limit_rejects_when_exceeded
          asserts 402 + mock_llm.assert_not_called().


BUG 7 — optimize_for accepted but never branched anything
--------------------------------------------------------------------------
File:     app/api/routes.py, app/db/schemas.py
Symptom:  optimize_for="quality" or "speed" behaved identically to the
          "cost" default — always ran the same truncation+routing
          pipeline no matter what the caller asked for. Also, the field
          was a bare `str`, so a typo like "qualtiy" silently fell through
          to default behavior instead of erroring.
Cause:    request.optimize_for was never read in create_message.
Fix:      - Context truncation now skipped when optimize_for == "speed"
            (computing embeddings adds latency, which is what "speed" mode
            is presumably asking to avoid).
          - Model routing now skipped when optimize_for == "quality" (never
            downgrade below the model the caller actually asked for).
          - Changed the schema field from `str` to
            `Literal["cost", "speed", "quality"]` so FastAPI now returns a
            422 for any other value instead of silently misinterpreting it.
Test:     test_create_message_optimize_for_quality_skips_routing,
          test_create_message_optimize_for_speed_skips_truncation,
          test_create_message_invalid_optimize_for_rejected.


BUG 8 — quality_threshold accepted but ignored (used the global default instead)
--------------------------------------------------------------------------
File:     app/api/routes.py, app/services/model_router.py
Symptom:  A caller passing a custom quality_threshold per request had no
          effect — routing always used settings.quality_threshold instead.
Cause:    ModelRouter.get_routing_decision() didn't even accept a
          quality_threshold parameter, so routes.py had nothing to pass
          through even if it wanted to.
Fix:      Added quality_threshold: Optional[float] = None to
          get_routing_decision(), forwarded to select_model(). routes.py
          now calls
            model_router.get_routing_decision(request.model, prompt_text, quality_threshold=request.quality_threshold)
Test:     test_get_routing_decision_quality_threshold_changes_model (proves
          a loose threshold picks haiku, a strict one picks opus, for the
          same prompt).


BUG 9 (found while fixing #8) — model routing accidentally gated behind
context truncation having fired
--------------------------------------------------------------------------
File:     app/api/routes.py
Symptom:  Model routing only ran `if settings.model_routing_enabled and
          len(optimizations_applied) > 0` — i.e. it silently never ran
          unless context truncation had already dropped at least one
          message. A short conversation (<= preserve_recent_messages)
          would never trigger truncation, so routing was skipped too, even
          though the two optimizations are logically independent. This
          would have made the "model routing" test scenario show nothing
          for any short prompt.
Cause:    Leftover/accidental coupling — `len(optimizations_applied) > 0`
          was presumably meant as some other condition and never revisited.
Fix:      Changed the gate to just `if settings.model_routing_enabled and
          request.optimize_for != "quality"` (see Bug 7) - routing now
          runs independently of whether truncation fired.


BUG 10 (found while fixing #8) — quality_threshold default on the wrong
scale, made routing always pick the cheapest model
--------------------------------------------------------------------------
File:     app/config.py, app/db/schemas.py
Symptom:  ModelRouter.QUALITY_SCORES are all 0-10 scale values (7.0-9.6).
          Both Settings.quality_threshold and
          MessagesCreateRequest.quality_threshold defaulted to `0.9` — a
          0-1 style number. Since every real quality score is >7x that
          threshold, EVERY task for EVERY model trivially passed the
          check, so select_model always returned the first (cheapest)
          entry in MODEL_ORDER: claude-haiku, regardless of task
          complexity. The core "intelligent routing" feature was
          non-functional by default - it always just picked Haiku.
Cause:    Default value copy-pasted from the README's example
          (`quality_threshold: float = 0.9  # Min acceptable quality`,
          written as if 0-1 normalized) without reconciling it against the
          actual 0-10 QUALITY_SCORES table used internally.
Fix:      Changed both defaults from 0.9 to 8.5 (0-10 scale). At 8.5:
          classification->haiku, summarization/coding->sonnet,
          general->sonnet - a meaningfully varied routing outcome across
          task types, instead of always Haiku.


MINOR — falsy-vs-None bug in select_model's threshold override
--------------------------------------------------------------------------
File:     app/services/model_router.py
Issue:    `quality_threshold = quality_threshold or self.quality_threshold`
          would incorrectly override an explicit `quality_threshold=0.0`
          with the instance default, since 0.0 is falsy. Same class of bug
          as Bug 5 (Phase 1) and the Phase 2 context_truncation rewrite
          already avoided. Not currently reachable with real values (0.0
          isn't a sane threshold on the 0-10 scale) but fixed for
          consistency: `quality_threshold if quality_threshold is not None
          else self.quality_threshold`.
