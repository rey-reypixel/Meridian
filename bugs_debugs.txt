MERIDIAN — BUGS FOUND & FIXED DURING PHASE 1 TESTING
======================================================
Date: 2026-08-08
Context: First test pass after scaffolding Phase 1 (Foundation). Local Python
was 3.7.9, incompatible with modern deps, so testing was done via Docker

BUG 1 — Wrong FastAPI import name
----------------------------------
File:     app/dependencies.py
Symptom:  App would crash immediately on import/startup.
Cause:    Imported `HTTPAuthCredentials` from `fastapi.security`, but that
          class doesn't exist. The real class is `HTTPAuthorizationCredentials`.
Fix:      Changed import and type hint:
              from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
              ...
              credentials: HTTPAuthorizationCredentials = Depends(security)


BUG 2 — Async/sync DB session mismatch
----------------------------------------
Files:    app/api/routes.py, app/api/auth.py, tests/conftest.py
Symptom:  Would raise `AttributeError: 'AsyncSession' object has no attribute
          'query'` on every database-touching endpoint (/api/messages,
          /api/dashboard/summary, /api/dashboard/models, /api/requests/{id},
          /auth/callback). Even where `.commit()` exists on AsyncSession, it's
          a coroutine — calling it without `await` means the commit silently
          never happens (data loss), no crash, no warning surfaced to caller.
Cause:    Routes were injecting `get_db_session` (an async generator yielding
          `AsyncSession` from db/database.py) but all the ORM code written
          against it used synchronous SQLAlchemy patterns: `db.query(...)`,
          `db.add(...)`, `db.commit()` without await.
          Meanwhile `app/dependencies.py`'s `get_current_user` was already
          correctly using a separate *synchronous* `get_db` (backed by
          `SessionLocal`) — so the two auth/db paths were inconsistent.
Fix:      Standardized on the synchronous `get_db` dependency everywhere
          (matches how the ORM code is actually written):
            - routes.py: swapped `Depends(get_db_session)` -> `Depends(get_db)`
              for all 4 endpoints, imported `get_db` from app.dependencies.
            - auth.py: same swap for the OAuth callback route.
            - tests/conftest.py: test fixture now overrides `get_db`
              (was overriding `get_db_session`, which no longer matched any
              route dependency, so the test db swap was silently doing
              nothing before this fix).
Note:     `get_db_session` (async) is still defined in db/database.py for
          future use, just not wired into any route right now.


BUG 3 — Missing email-validator dependency
---------------------------------------------
File:     app/db/schemas.py (uses `EmailStr` from pydantic)
Symptom:  ImportError at import time: "email-validator is not installed,
          run `pip install 'pydantic[email]'`" — took down the whole app
          since schemas.py is imported by routes.py at module load.
Cause:    `pydantic.EmailStr` requires the optional `email-validator`
          package, which wasn't listed in requirements.txt.
Fix:      Added `pydantic[email]` to backend/requirements.txt.


BUG 4 — Missing numpy dependency
------------------------------------
File:     app/services/context_truncation.py
Symptom:  ModuleNotFoundError: No module named 'numpy'.
Cause:    File does `import numpy as np` (used for embedding vectors, ahead
          of full Phase 2 FastEmbed integration) but numpy was never added
          to requirements.txt.
Fix:      Added `numpy` to backend/requirements.txt.


BUG 5 (minor / code smell) — Mutable default on SQLAlchemy JSON column
--------------------------------------------------------------------------
File:     app/db/models.py
Symptom:  Not yet triggered in practice (routes.py always passes
          `optimizations_applied` explicitly), but a real landmine: SQLAlchemy
          column defaults should be callables, not shared mutable objects.
          Using a literal `[]` means every row that relies on the column
          default shares the *same* list instance.
Cause:    `optimizations_applied = Column(JSON, default=[])`
Fix:      `optimizations_applied = Column(JSON, default=list)`

DESIGN NOTE — batching vs. a synchronous HTTP API
--------------------------------------------------------------------------
Anthropic's real Message Batches API has ~24h turnaround, which doesn't
fit a request/response HTTP endpoint. Implemented instead: requests with
batch=true get pushed onto a Redis list keyed by (model, task_type); once
the group hits batch_size or sits past batch_timeout, a Celery task
(meridian.process_batch, in app/celery_app.py) pops the group and calls
Claude sequentially for each item in the *worker* container, storing each
result back in Redis under its own request_id. The original HTTP handler
polls (via run_in_threadpool, so it doesn't block the event loop) for its
own request_id's result.

Gap: there's no Celery beat/periodic flush (explicit Phase 2 scope
decision), so a batch with no further arrivals just sits until something
checks it. Safety net: if a request's own wait_for_result poll times out
(15s), it force-flushes its batch inline rather than hanging forever or
erroring for no reason. Verified both paths actually happen (see live
tests below) — a 2-request batch with batch_size=2 flushed for real via
Celery .delay() and showed up in the worker's logs; a lone 1-request
batch (nothing to fill it) correctly fell through to the inline fallback
after its wait timed out.

PHASE 2.5 — found while wiring up 3 previously-dead request params
======================================================
Date: 2026-08-08 (same day, continued)
Context: Before testing against a real Anthropic API key, checked whether
MessagesCreateRequest's advertised parameters (cost_limit, optimize_for,

BUG 6 — cost_limit accepted but never enforced
--------------------------------------------------------------------------
File:     app/api/routes.py (create_message)
Symptom:  A caller could pass cost_limit=0.50 ("don't spend more than
          this") and it did nothing — request always went through
          regardless of estimated cost. Directly contradicts the README's
          advertised budgeting feature.
Cause:    request.cost_limit was never read anywhere in the function.
Fix:      After computing optimized_cost (the pre-call estimate) and
          before any LLM/batch call, added:
            if request.cost_limit is not None and optimized_cost > request.cost_limit:
                raise HTTPException(402, detail=f"Estimated cost ... exceeds cost_limit ...")
          Placed before the Claude API call specifically so a request that
          would exceed budget never spends anything.
Test:     tests/test_routes.py::test_create_message_cost_limit_rejects_when_exceeded
          asserts 402 + mock_llm.assert_not_called().


BUG 7 — optimize_for accepted but never branched anything
--------------------------------------------------------------------------
File:     app/api/routes.py, app/db/schemas.py
Symptom:  optimize_for="quality" or "speed" behaved identically to the
          "cost" default — always ran the same truncation+routing
          pipeline no matter what the caller asked for. Also, the field
          was a bare `str`, so a typo like "qualtiy" silently fell through
          to default behavior instead of erroring.
Cause:    request.optimize_for was never read in create_message.
Fix:      - Context truncation now skipped when optimize_for == "speed"
            (computing embeddings adds latency, which is what "speed" mode
            is presumably asking to avoid).
          - Model routing now skipped when optimize_for == "quality" (never
            downgrade below the model the caller actually asked for).
          - Changed the schema field from `str` to
            `Literal["cost", "speed", "quality"]` so FastAPI now returns a
            422 for any other value instead of silently misinterpreting it.
Test:     test_create_message_optimize_for_quality_skips_routing,
          test_create_message_optimize_for_speed_skips_truncation,
          test_create_message_invalid_optimize_for_rejected.


BUG 8 — quality_threshold accepted but ignored (used the global default instead)
--------------------------------------------------------------------------
File:     app/api/routes.py, app/services/model_router.py
Symptom:  A caller passing a custom quality_threshold per request had no
          effect — routing always used settings.quality_threshold instead.
Cause:    ModelRouter.get_routing_decision() didn't even accept a
          quality_threshold parameter, so routes.py had nothing to pass
          through even if it wanted to.
Fix:      Added quality_threshold: Optional[float] = None to
          get_routing_decision(), forwarded to select_model(). routes.py
          now calls
            model_router.get_routing_decision(request.model, prompt_text, quality_threshold=request.quality_threshold)
Test:     test_get_routing_decision_quality_threshold_changes_model (proves
          a loose threshold picks haiku, a strict one picks opus, for the
          same prompt).


BUG 9 (found while fixing #8) — model routing accidentally gated behind
context truncation having fired
--------------------------------------------------------------------------
File:     app/api/routes.py
Symptom:  Model routing only ran `if settings.model_routing_enabled and
          len(optimizations_applied) > 0` — i.e. it silently never ran
          unless context truncation had already dropped at least one
          message. A short conversation (<= preserve_recent_messages)
          would never trigger truncation, so routing was skipped too, even
          though the two optimizations are logically independent. This
          would have made the "model routing" test scenario show nothing
          for any short prompt.
Cause:    Leftover/accidental coupling — `len(optimizations_applied) > 0`
          was presumably meant as some other condition and never revisited.
Fix:      Changed the gate to just `if settings.model_routing_enabled and
          request.optimize_for != "quality"` (see Bug 7) - routing now
          runs independently of whether truncation fired.


BUG 10 (found while fixing #8) — quality_threshold default on the wrong
scale, made routing always pick the cheapest model
--------------------------------------------------------------------------
File:     app/config.py, app/db/schemas.py
Symptom:  ModelRouter.QUALITY_SCORES are all 0-10 scale values (7.0-9.6).
          Both Settings.quality_threshold and
          MessagesCreateRequest.quality_threshold defaulted to `0.9` — a
          0-1 style number. Since every real quality score is >7x that
          threshold, EVERY task for EVERY model trivially passed the
          check, so select_model always returned the first (cheapest)
          entry in MODEL_ORDER: claude-haiku, regardless of task
          complexity. The core "intelligent routing" feature was
          non-functional by default - it always just picked Haiku.
Cause:    Default value copy-pasted from the README's example
          (`quality_threshold: float = 0.9  # Min acceptable quality`,
          written as if 0-1 normalized) without reconciling it against the
          actual 0-10 QUALITY_SCORES table used internally.
Fix:      Changed both defaults from 0.9 to 8.5 (0-10 scale). At 8.5:
          classification->haiku, summarization/coding->sonnet,
          general->sonnet - a meaningfully varied routing outcome across
          task types, instead of always Haiku.


MINOR — falsy-vs-None bug in select_model's threshold override
--------------------------------------------------------------------------
File:     app/services/model_router.py
Issue:    `quality_threshold = quality_threshold or self.quality_threshold`
          would incorrectly override an explicit `quality_threshold=0.0`
          with the instance default, since 0.0 is falsy. Same class of bug
          as Bug 5 (Phase 1) and the Phase 2 context_truncation rewrite
          already avoided. Not currently reachable with real values (0.0
          isn't a sane threshold on the 0-10 scale) but fixed for
          consistency: `quality_threshold if quality_threshold is not None
          else self.quality_threshold`.

verifiable at $0: embedding-based task classification (replacing keyword
matching), semantic response caching, streaming responses, and real load

and multi-provider support were discussed but need paid API calls to
verify, so deferred.)

Status: DONE. Build, full test suite (68/68), and live verification
against the real running stack (Postgres/Redis/Celery, MOCK_ANTHROPIC=true)
including a real Locust load-test run all complete - see the LIVE
VERIFICATION and REAL LOAD TEST RESULTS sections below.

WHAT WAS BUILT
---------------
1. New app/services/embeddings.py - EmbeddingService, extracted out of
   context_truncation.py so the FastEmbed model + Redis cache load once
   and get shared across context truncation, task classification, and
   response caching (previously only context_truncation.py owned this;
   loading a second copy for the new consumers would've doubled memory
   and cold-start time). context_truncation.py now delegates to it.

2. app/services/model_router.py: classify_task() now embeds the prompt
   and compares it via cosine similarity against TASK_EXAMPLES (a few
   canonical prompts per category), instead of brittle keyword matching
   (`"classify" in prompt.lower()`). Falls back to "general" if even the
   best match scores below task_classification_min_confidence (0.3).

3. New app/services/response_cache.py - Redis-backed semantic cache, keyed
   per model. A near-duplicate prompt (cosine similarity >=
   response_cache_similarity_threshold, default 0.97 - deliberately high,
   since a wrong hit is worse than a miss) returns the cached response
   instead of calling the LLM. FIFO eviction past
   response_cache_max_entries (200/model), TTL 1h. Only checked/populated
   when request.temperature <= response_cache_max_temperature (0.3) -
   reusing a stale response instead of sampling a new one isn't obviously
   correct for high-temperature/creative requests, so those are excluded
   rather than pretending this is solved.

4. Streaming: app/services/llm_client.py gained stream_message() (a
   second AsyncAnthropic client for real async streaming; mock mode
   yields the same [MOCK RESPONSE] text word-by-word so streaming is also
   testable at $0). New POST /api/messages/stream endpoint (SSE), rejects
   batch=true with 400 (streaming a deferred/grouped batch result isn't a
   coherent combination without a much bigger pub/sub redesign - out of
   scope). Checks/populates the response cache same as the direct
   endpoint; on a cache hit, fake-streams the cached text in word-chunks
   instead of hitting the LLM.

5. backend/loadtest/ - locustfile.py + setup_test_user.py, ready to run
   against the live stack with MOCK_ANTHROPIC=true (free, and it's
   actually the *correct* way to isolate Meridian's own routing/
   truncation/DB overhead from Claude's response time, which is what the
   README's latency claims are really about).

BUGS / DESIGN ISSUES FOUND WHILE BUILDING THIS
------------------------------------------------
Real inefficiency fixed: classify_task() was being called up to 3x per
request (inside select_model, again in get_routing_decision, again in
routes.py's batch block) - harmless with cheap keyword matching, wasteful
once it's an embedding + N-example similarity computation. Refactored
model_router.py so select_model()/get_routing_decision() both accept an
optional pre-computed task_type, and routes.py's new
_prepare_optimized_request() helper (extracted from create_message, now
shared with the new streaming endpoint) classifies once and threads the
result through everywhere, including the batch block.

Real design question resolved: does the DB session injected via
Depends(get_db) stay valid for the full lifetime of a StreamingResponse
generator, or does FastAPI close it once the endpoint function returns
(before the stream finishes)? Rather than trust version-dependent
behavior here, create_message_stream's generator opens its own
SessionLocal() directly and closes it in a finally block, so the DB
write's lifetime is self-contained and correct regardless of FastAPI/

FRONTEND/UX GAP ANALYSIS — backend data vs. the design brief
======================================================
Date: 2026-08-09
Context: Before any frontend code was written, inspected what the actual
backend returns against a detailed design brief (dark "infrastructure
console" aesthetic, specific pages: Overview, Optimizations, Requests,
Analytics, Settings). Recording this because two small backend additions
were made as a direct result (GET /api/requests, token/latency in the
summary endpoint - see the commit "Add GET /api/requests list endpoint,
aggregate tokens/latency into dashboard summary"), and because the
remaining gaps below determine what the frontend can wire to real data
today vs. what needs mock data or new backend work.

What ApiRequest actually stores per row: original_model, routed_model,
original_cost, optimized_cost, savings, optimizations_applied (list),
quality_score, input_tokens, output_tokens, latency_ms, created_at.
No prompt/message text is ever persisted.

Maps cleanly to real data today:
- Overview KPIs: total spend/saved/savings %/avg quality (no sparklines)
- Model Mix donut (usage_count -> percentage, from /api/dashboard/models)
- Requests table: id, timestamp, original/routed model, costs, savings,
  optimizations_applied, quality_score, latency (via the new

Still gaps (need mock data, or new backend work, to build these):

  the current data model; savings is one combined number per request,

ISSUE 1 — Docker build ran out of disk space mid-build
--------------------------------------------------------------------------
Instance: EC2 t3.micro, Ubuntu 26.04 LTS, default 8GB root EBS volume.
Symptom:  `docker compose up -d` failed for both backend and worker
          images with "write ... no space left on device" partway
          through unpacking the built image layers.
Cause:    8GB is genuinely too small to build two ~1GB Python images
          (FastEmbed pulls in onnxruntime, Locust pulls in gevent - both
          add real weight) on top of the Ubuntu base + Docker's own
          intermediate build layers, which temporarily use more space
          than the final images before cleanup.
Fix:      Resized the EBS volume 8GB -> 20GB via EC2 Console -> Volumes
          -> Modify Volume (gp3 free tier covers up to 30GB/month, so
          this cost nothing extra). Ubuntu's cloud-init auto-grew the
          actual root filesystem on the resize event - manual
          `growpart`/`resize2fs` against the specific NVMe partition
          reported "NOCHANGE... cannot be grown" (it was pointed at the
          wrong partition in the AMI's layout) but this was harmless
          noise since cloud-init had already done the real work; `df -h`
          confirmed 13GB free afterward. Then `docker system prune -f`
          to clear the failed build's partial layers, and retried
          `docker compose up -d postgres redis backend worker`
          successfully.


ISSUE 2 — SSH connection timed out after editing the security group
--------------------------------------------------------------------------
Symptom:  SSH access worked fine initially. After going into the EC2
          security group console to add inbound rules for Caddy (ports
          80/443), `ssh -i meridian.pem ubuntu@<ip>` started timing out
          entirely - not "connection refused," a full timeout (suggests
          traffic wasn't reaching the instance on port 22 at all).
Cause:    Not confirmed with certainty (didn't diff the exact before/
          after rule set), but the most likely explanation: the SSH
          rule's Source was originally set via "My IP" at instance
          launch time, capturing whatever the home ISP's public IP was
          at that moment. Home IPs aren't static - it had very likely
          changed since then, and re-selecting "My IP" fresh (which
          re-detects the CURRENT address) during the same edit session
          that added the HTTP/HTTPS rules coincided with this being
          discovered, since that's when the mismatch actually got
          checked/fixed.
Fix:      EC2 -> Security Groups -> the instance's group -> Edit inbound
          rules -> SSH row -> Source dropdown -> re-select "My IP" (forces
          a fresh detection) -> Save. SSH connected immediately after.
Lesson for next time: if SSH mysteriously stops working with no config
changes on the *SSH rule itself*, check whether the home IP simply
changed before assuming something else broke - this is a common false
alarm that looks like a "we broke it" bug but is actually just DHCP churn
on the client side.

FRONTEND ISSUE 1 — authenticated user bounced back to /login right after
a successful token exchange
--------------------------------------------------------------------------
Symptom:  Minted a real JWT via the backend (same SessionLocal +
          create_access_token pattern used throughout backend testing),
          navigated to /auth/callback?token=<jwt>. AuthCallback correctly
          stored the token in localStorage and called navigate('/'), but
          the app landed back on /login instead of the authenticated
          shell - even though calling GET /auth/me with that exact token
          (both via curl-equivalent fetch and via the app's own
          getCurrentUser() called manually) returned 200 with the correct
          user every time.
Cause:    Race condition in useAuth's `isLoading` derivation. TanStack
          Query v5 defines `isLoading` as `isPending && isFetching`. The
          `currentUser` query starts with `enabled: hasToken`, which
          flips false -> true the instant the token is stored. On the
          very next render, `isPending` is already true (no data yet) but
          `isFetching` hasn't ticked over yet - the actual fetch kicks
          off in an effect that fires after that render commits. So for
          one render, `isLoading` reads false while `isAuthenticated`
          (`!!user`) is also false, and ProtectedRoute treats that as "not
          loading, not authenticated" and redirects to /login. The
          `/auth/me` fetch then completes normally in the background, but
          nothing on the Login page reacts to becoming authenticated, so
          the user stays stuck on /login despite holding a valid token.
Fix:      Swapped `isLoading` for `isPending` in the useQuery destructure
          in dashboard/src/hooks/useAuth.tsx, and derived the context's
          `isLoading` as `hasToken && isPending` instead of
          `hasToken && isLoading`. `isPending` stays true for the entire
          window between "no data yet" and "settled (success or error)",
          independent of whether a fetch is actively in flight, which
          closes the race. Also added a defensive `isAuthenticated` check
          to the top of Login.tsx that redirects to `/` if already
          authenticated, as a second line of defense for any other path
          that lands an authenticated user on /login.
Verified: Fresh browser tab, minted JWT, navigated straight to
          /auth/callback?token=<jwt> - landed on the real authenticated
          shell (Sidebar showing "Frontend Test User" /
          frontend-test@example.com, both pulled live from /auth/me, not
          hardcoded), zero console errors. Hard-reloaded directly on
          /requests (not a SPA navigation) to confirm the token-based
          re-auth also works on a fresh page load, not just the
          in-session redirect right after /auth/callback - correctly
          rendered the protected route instead of bouncing to /login.


FRONTEND ISSUE 2 — Request Detail's error state never rendered for a
missing request ID (stuck in loading skeleton forever)
--------------------------------------------------------------------------
Symptom:  Navigated to /requests/<id-that-does-not-exist> to test the 404
          path. GET /api/requests/<id> correctly returned 404 with a real
          error body, but the page just sat on the loading skeleton
          forever - ErrorState never appeared, even after waiting several
          seconds and confirming (via curl and via the app's own api.get()
          called manually) that the backend and the API client both
          behaved correctly.
Cause:    dashboard/src/api/requests.ts's useRequestDetail didn't set a
          `retry` option, so it inherited the QueryClient's global default
          (`retry: 1`). Added a temporary diagnostic log of the query's
          raw status/fetchStatus (same technique used earlier for the
          Sidebar investigation) and found `fetchStatus: 'paused'` - that
          value only occurs when TanStack Query v5's networkMode:'online'
          logic decides the browser is offline and pauses a queued retry.
          Root cause is almost certainly specific to this browser-
          automation sandbox mis-firing an 'offline' event at some point
          (navigator.onLine and onlineManager.isOnline() both read `true`
          when checked directly, yet the already-paused retry never
          resumed) rather than a real connectivity issue - consistent
          with the other "browser automation tooling quirks" already
          noted in this project (transient Vite dep re-optimization
          causing invalid-hook-call errors, `computer` click coordinates
          occasionally not registering - see below). Separately from the
          environment quirk, retrying a 404 on one specific request ID is
          pointless regardless of environment - the ID either exists or
          it doesn't, and no amount of retrying changes that.
Fix:      Set `retry: false` explicitly on useRequestDetail's query. This
          is the correct behavior on its own merits (no wasted requests
          retrying a deterministic not-found), and it also sidesteps the
          retry-pause path entirely since there's no retry to pause.
Verified: Fresh tab, same nonexistent ID -> ErrorState rendered
          immediately ("COULD NOT LOAD REQUEST" / "This request may not
          exist, or the request failed to load." / Retry button), single
          404 request in the network log, zero stuck-loading state.

Also observed during this same investigation: the `computer` tool's click
action occasionally reported success (correct coordinates, matched the
target element's real bounding box) without the click actually reaching
the page - confirmed by dispatching `.click()` on the same DOM element
via javascript_tool immediately after, which worked instantly. Not a
product bug; noted here only so a future "the button doesn't work"
investigation in this environment checks a programmatic click before
assuming the app is broken.


FRONTEND ISSUE 3 — /auth/callback path collision when frontend and
backend share one origin (live deploy only, invisible in local dev)
--------------------------------------------------------------------------
Symptom:  First live deploy of the dashboard to
          https://meridianpixelated.duckdns.org (frontend and backend now
          served from the same domain via Caddy, unlike local dev where
          they're on separate ports 3000/8000). Google's OAuth redirect
          landing page (dashboard/src/pages/AuthCallback.tsx, route
          /auth/callback, reads ?token=) never rendered - every hit to
          /auth/callback got a raw JSON 422 from the backend

Cause:    Two different things both legitimately needed the exact same
          path /auth/callback:

          origins (localhost:3000 vs localhost:8000). Once both sat
          behind the same Caddy host for the live deploy, the Caddyfile's
          `handle /auth/* { reverse_proxy localhost:8000 }` rule sent
          EVERY /auth/callback request straight to the backend - Google's
          real hit (?code=) as well as the backend's own redirect back to
          "the frontend" (?token=), since both used the identical path.
          The browser never got a chance to load the SPA at that path.

          /auth/callback to /auth/google/callback (safe to rename freely

          Updated OAUTH_REDIRECT_URI (config.py default, .env.example,
          and the live server's .env) to match. Updated the live
          Caddyfile to whitelist the specific real backend auth paths
          (/auth/login, /auth/google/*, /auth/me, /auth/logout) instead
          of blanket-proxying /auth/*, so /auth/callback now correctly
          falls through to the SPA's static files. /auth/callback itself
          is now exclusively the frontend's route - the backend never
          owns it.
Verified: Minted a real JWT on the live server, hit
          https://meridianpixelated.duckdns.org/auth/callback?token=<jwt>
